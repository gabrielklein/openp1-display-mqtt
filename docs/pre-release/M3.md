# M3: Wi-Fi provisioning and read dashboard

M3 accepted by user report on 2026-10-24 after software checks. The user
confirms M3 validation; individual phone versions and bench logs were not
supplied. No agent flashing was performed. M2 display/replay acceptance was
reported by the user on 2026-10-23; electrical meter compatibility is unverified.

## Behaviour

With no saved network, join the open `OpenP1-<last three MAC bytes>` AP and open
`http://192.168.4.1/setup`. The screen alternates network information with its
last reading pair; other readings and the SIMULATION heading remain visible.
The original ESP-IDF wizard has three steps: select a network, enter Wi-Fi
credentials, then follow connection progress. Network cards show signal quality
and open/protected status; manual SSID entry supports hidden networks. No
NetWizard code, assets or library is imported, and Arduino is not added.
The interface is served entirely from firmware, without CDN or Internet access. Captive DNS answers bounded, uncompressed single-question
IPv4 requests; HTTP probe paths redirect to the manual setup address. Android
and iOS automatic popup detection is best effort, not verified here.

Credentials are tried for 30 seconds and saved in NVS only after an IP is
obtained. On failure the setup AP stays available for another attempt. After
success, the wizard exposes the new station IP and keeps the setup-only AP
available for ten seconds, then closes it. The user joins their usual Wi-Fi to
open the dashboard. The screen shows the station IP after AP closure. A configured
installation reconnects with exponential delays capped at 60 seconds; it never
forgets credentials or opens setup because of a network outage. NVS errors
fail closed without automatic erasure. The original M3 default was View; the current default is Full with a one-time
View-default migration (see M4.md);
existing None/View/Full is respected. Policy mutation and S2 are M4 work.
There is no application password. Provisioning uses an open AP and HTTP;
credentials are stored in ordinary NVS, without flash encryption claims.

At `http://<screen-IP>/`, the embedded responsive dashboard polls every two
seconds. `/api/v1/status` and `/api/v1/values` return JSON, including simulation,
errors, uptime, connection and stale state. Numeric and string OBIS readings (including serial/GR identifiers)
retain individual monotonic timestamps and original units where applicable; missing values are
absent, not zero-filled. Samples become stale at 15 seconds. On HTTP failure
the dashboard marks retained rows unavailable. Numbers are double projections;
exact A-XDR bytes remain in the meter processor and bounded presentation pool.
The read API renders string/octet values as UTF-8 when printable and valid,
otherwise as lossless hex with `value_encoding: "hex"`. Strings are never
converted to numbers, preserving leading zeroes.

## Ownership, bounds and guards

Acquisition publishes at most 64 readings and an 8192-byte pool of exact encoded
values using a nonblocking
mutex attempt; missed snapshots coalesce at the next 250 ms update. It never
waits for HTTP, DNS, scanning, Wi-Fi connection or flash persistence. HTTP reads
its own heap-allocated bounded copy to avoid exceeding its task stack. Network state is mutex protected. HTTP uses three client sockets,
12 KiB task stack, a 4096-byte request-header limit and three-second
send/receive timeouts; the network worker uses 6 KiB, including bounded scan
result collection. Scan starts asynchronously in that worker and completes
through the ESP-IDF scan event; HTTP never waits for the radio scan. Results
hold at most 16 SSIDs (33 bytes including terminator), RSSI and security flags;
new scans start no more than once per ten seconds, with a ten-second radio
scan deadline. Repeated reads within that interval use cached results. JSON bodies are bounded to 384 bytes with a three-second receive
budget. SSID is 1–32 bytes;
password is empty for open Wi-Fi or 8–63 bytes. 64-character hex PSKs and
enterprise authentication are not supported.

Every HTTP request checks setup state and persisted access policy. Setup never
serves meter data or diagnostics, including to existing connections. None
blocks dashboard and read API. Unimplemented routes cannot grant access.
Provisioning writes require a per-boot random header token, canonical Host,
same-origin Origin when supplied, and JSON content type. No CORS is enabled.
Secrets are never returned, echoed or logged by application code. The UI uses
textContent for meter/network text. No streaming connection is introduced;
stream revocation and temporary elevation remain M4 work.

## Checks and physical acceptance

Software checks: `sh scripts/test-native.sh`, `node scripts/test-web.cjs`, `sh scripts/test-http.sh`,
network model with AddressSanitizer/UndefinedBehaviorSanitizer, and PlatformIO
ESP-IDF builds. See CHANGELOG.md for the actual configurations checked.
Native network checks cover credential bounds, backoff limits, stale boundary,
DNS truncation, compression/AAAA rejection, response bounds and 10,000 malformed
packets. Embedded-script checks exercise simulation, stale/unavailable/recovery,
untrusted display strings, asynchronous scan selection, manual entry, connection
polling, success/failure/retry, duplicate submission and password clearing.
HTTP tests compile the real handlers with host transport/mutex doubles and the
bundled ESP-IDF cJSON; they exercise scan states, setup status secret exclusion,
canonical-host redirects, access guards, busy writes and CSRF rejection.
They do not simulate the ESP-IDF radio, TCP stack or NVS on hardware. No browser
was available through the UI tool for visual QA; mobile layout and captive
behaviour still require the physical checks below.

Acceptance checklist (user reports M3 validated; keep for reproducible retests):

1. On an unconfigured board, confirm AP name and manual address are readable.
   Test popup/manual provisioning on Android and iOS, scan and hidden/manual SSID.
2. Check wrong password, connection timeout and retry; reboot before successful
   provisioning and confirm setup remains available. Verify password is absent
   from responses, screen and serial application logs.
3. Connect successfully, confirm the AP closes and the displayed station IP
   opens the dashboard; reboot and confirm credential/policy persistence.
4. Interrupt the router, confirm bounded reconnect attempts, no fallback AP,
   then recovery after router restoration while acquisition continues.
5. In replay, confirm values/units, SIMULATION, per-value age and stale state
   after 15 seconds. Test disconnected browser and recovery. Test empty UART.
6. Verify setup denies `/api/v1/values`, and None denies dashboard/API requests,
   including on an already open HTTP connection. Full/View permit read routes.
   Setting policies for this check currently requires a controlled NVS fixture;
   the S2/config UI and complete access matrix arrive in M4.

User-reported acceptance above permits progression to M4. MQTT, raw/export API,
configuration/replay controls, Wi-Fi reset button, WebSocket and full diagnostics
are not implemented by M3.

References: ESP-IDF 5.3.1 [Wi-Fi API](https://docs.espressif.com/projects/esp-idf/en/v5.3.1/esp32/api-reference/network/esp_wifi.html)
and [HTTP server](https://docs.espressif.com/projects/esp-idf/en/v5.3.1/esp32/api-reference/protocols/esp_http_server.html).

## Provisioning endpoints

Only during setup (including the ten-second success interval):

- `GET /setup/token`: per-boot CSRF token, never Wi-Fi credentials.
- `GET /setup/scan`: HTTP 202 `{ "state": "scanning" }`, then HTTP 200
  `{ "state": "ready", "networks": [{ "ssid": "…", "rssi": -60, "secure": true }] }`.
  Busy connection returns 409; scan failure returns 503. Cached results may be
  returned for ten seconds. Unknown/empty SSIDs are omitted by the UI.
- `POST /setup/wifi`: bounded `{ "ssid": "…", "password": "…" }`, existing
  token/Host/Origin guards; reject overlapping scans or connection attempts.
- `GET /setup/status`: `idle`, `connecting`, `saving`, `success`, `failed`,
  `timeout` or `storage_error`. Only `success` adds `ip`. No credentials,
  meter readings or diagnostics are included. This route becomes unavailable
  when setup closes; it is not an exception to the station access policy.

The wizard polls scans/status at one-second intervals, with bounded iteration
counts and seven-second HTTP request deadlines. Lost AP connection prompts the
user to check the physical display instead of claiming successful provisioning.
For HTTP handler tests, `IDF_PATH` may select the installed pinned SDK package;
otherwise the script uses `~/.platformio/packages/framework-espidf`.

## Dashboard OBIS presentation

The table separates measurement name, OBIS, value and age. `obis` in the API
keeps all six dotted components for machine compatibility; `obis_display` uses
`A-B:C.D.E`, omitting `*255` only. Other F values remain as `*F`, and A/B channel
values are preserved (for example `1.0.1.8.1.255` becomes `1-0:1.8.1`).
Energy registers C=1/2, D=8 are labelled `Import +A` / `Export -A` with `total`
for E=0 or `tariff N` for other transmitted tariff indices, including 3–7 and
beyond. Values and units still come from decoded data/scalers, never the label.
The current meter-specific identifier labels assume `0-0:96.1.0` is the serial
number and `0-0:96.1.1` is the GR number; the user has been asked to confirm this
correspondence. Other strings retain their OBIS and are shown as unknown objects.
