# M6: Full-access web firmware update

New M6 requested on 2026-10-26. Former M6 hardware/release work moves to M7.
M6 accepted by user report on 2026-10-26; local milestone tag v0.6.0.

## Version and build

Firmware versions use a valid date, e.g. `2026.10.26`, from `VERSION`. ESP-IDF's
application descriptor, boot log, status API and Settings expose the actual built
version. Milestone Git tags remain separate from date-based firmware versions.

```sh
python3 scripts/build-firmware.py
# Optional date for a particular build:
python3 scripts/build-firmware.py --version 2026.10.27
```

The script uses the pinned tenstar_tdisplay environment and never uploads or
opens a device. It produces `dist/openp1-display-<date>.bin`, `.sha256` and `.json`
metadata. Only the application `.bin` is uploaded in the browser. The script
verifies chip/project/version, image bounds and appended SHA256 before packaging.
Date-specific build directories avoid stale version descriptors; a custom
`--build-dir` is cleaned if its recorded version differs. `--pio` can select the
PlatformIO executable. Build outputs are ignored by Git. Same-date rebuilds are
allowed; use the sidecar hash to identify an exact file. Downgrades are allowed
if they meet the same validation rules; eFuse anti-rollback is not configured.

## One-time migration from the old layout

The old factory-only layout has no inactive update slot. Install this revision
once using the normal PlatformIO USB upload, which installs the bootloader,
partition table, initial OTA metadata and factory application. The assistant
has not performed this operation. Disconnect the complete meter cable before
USB; never power from meter and USB simultaneously.

The 16 MiB layout keeps NVS at 0x9000, PHY at 0xf000 and the 3 MiB factory app
at 0x10000. It adds otadata at 0x310000 and two 3 MiB OTA slots at 0x320000 and
0x620000. The unused/unmounted storage partition moves to 0x920000. NVS settings
remain at their existing addresses. This repurposes the old reserved storage
area; the current firmware has never mounted it or stored captures there. Board
flash capacity/electrical verification remain M7 work.

Do not try to migrate by uploading a partition table, merged image or bootloader
through the web form. The web updater rejects unsupported layouts and accepts
application-only binaries. After the USB migration, later updates alternate
between OTA slots and leave the running application/factory fallback untouched.

## Web flow and access

Settings → Firmware update shows the installed date version and a `.bin` file
selector. The GET/PUT `/api/v1/firmware` endpoints require Full access and the
station origin. PUT requires the session CSRF token and application/octet-stream.
Setup AP/View/None cannot update. Uploads use one 1024-byte buffer plus a bounded
288-byte descriptor prefix, with a 3 MiB cap and 180-second deadline. Header
fragmentation is supported. No complete image is held in RAM.

The first prefix must identify classic ESP32, project openp1_display, a valid date
and an appended SHA256 digest. Then esp_ota_begin uses incremental erase, writes
only the inactive slot and yields between chunks. Access is checked before and
after reads/writes, after validation and before boot selection. Expiry, transport
failure, timeout or write failure aborts the active OTA handle without selecting
the partial image. ESP-IDF performs final checksum/hash/chip/image validation;
only success permits esp_ota_set_boot_partition. Further uploads are rejected
while a selected boot image awaits restart, preventing replacement of the selected
slot during the reboot delay. SDK failures do not select the image. User-supplied images are not cryptographically publisher-signed: hash
verification checks integrity, not publisher identity. Full is the existing LAN
access policy, not a new password/login. Use the existing trusted-LAN model.

During upload, the page disables actions and stops status polling, uses a long
request deadline and never retries writes automatically. Success displays the
English restarting page and schedules reboot. If the response is lost after
boot selection, the reboot still proceeds; check the displayed version afterward.
Settings are preserved. Keep power stable during upload and restart. Flash writes
can add latency to acquisition; uninterrupted meter sampling is not claimed.

## Startup confirmation and rollback

Bootloader rollback is enabled and required. Existing generated profiles with
rollback disabled must enable **Bootloader config → Enable app rollback support**
in `pio run -e tenstar_tdisplay -t menuconfig`; the application compile guard
rejects a disabled profile. A newly booted OTA image remains
pending verification. Acquisition calls the startup check after initialization;
after 30 seconds of uptime it confirms the image only when network/HTTP worker
initialization succeeded and acquisition has reached its update loop. Broker
connection and incoming meter data are not required. Failed network initialization
requests rollback. A reset/crash before confirmation invokes ESP-IDF rollback to
the previous bootable app; this does not detect arbitrary bugs after confirmation.
The updater refuses another upload while the running image is pending verification.
Factory boots have no pending OTA state. Failed state reads/confirmation are retried.

## Verification and remaining acceptance

Host transport doubles check Full/View/None/setup/origin/CSRF, unsupported layout,
wrong chip/project/date/hash flag, size bounds, fragmented upload byte fidelity,
SDK write/end/select failures, truncated input, expiry during upload and after
validation, timeout, successful restart scheduling and startup confirmation/
rollback requests. These are control-flow checks, not cryptographic/physical
ESP-IDF execution. Packager tests independently check real built image SHA256 and
malformed/date cases. Embedded UI tests verify the binary body/token and restart.

User acceptance (2026-10-26): after the proposed checklist covering the initial
USB installation, a different dated build, Full-access web upload, restart/version,
settings preservation, MQTT recovery, invalid-image rejection and rollback, the
user confirmed that these steps work. M6 is closed on that report with local
v0.6.0. No exact flashed image hash, rollback trigger, interruption/power-loss
procedure or timing evidence was supplied; do not infer exhaustive fault testing.
The assistant did not flash hardware. M7 remains hardware/release validation.
